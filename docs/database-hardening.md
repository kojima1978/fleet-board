# DB整合性と利用開始時点の履歴

## 変更の範囲

`20261031100000_history_integrity`を追加し、開発・本番で共通のSQL移行を使う構成にしました。既存の社員・車両・利用記録は削除しません。不要項目の削除、利用履歴の保持年数、操作ログの構造化は別の変更として扱います。

## 利用開始操作時の登録情報

Tripに次の項目を追加しています。

- snapshotCapturedAt：登録情報を取得した日時
- employeeNameAtStart / employeeCodeAtStart / departmentNameAtStart：利用者の氏名・番号・部署
- vehicleNameAtStart / vehicleCodeAtStart / plateNumberAtStart：車両の名前・番号・ナンバー

利用開始のトランザクション内で取得・保存し、予約段階では保存しません。予約後に登録情報が変わった場合も、実際の利用開始操作時の情報を保存します。保存済みの情報はDBトリガーで上書き・消去を拒否します。実際の開始時刻の訂正、返却、返却取消では変更しません。日時訂正で過去へ時刻を直しても、その時点の登録情報を推測して置き換えません。

導入前の記録は全項目NULLのまま残します。履歴画面は現在の登録情報を代わりに表示し、「当時の登録情報未保存・現在の情報を表示」と明示します。旧バックアップも同じ扱いです。社員・車両の固定IDと現在の登録情報も維持し、当時の情報と現在の名前の両方で利用者名を検索できます。

## DB側で守る条件

| 対象 | 条件 |
| --- | --- |
| 利用記録 | 予定終了は開始より後。実績終了は開始以降。予約・取消／利用中／完了と実績日時の組合せが一致 |
| 利用中 | 同一車両・同一社員はそれぞれ1件まで |
| 整備 | 予定・実績の日時の順序と状態が一致。同一車両の整備中は1件まで |
| ガソリン残量 | 現在値・返却時点・取消復元用の値はNULLまたは0〜4 |
| NFC | 所有者は社員か車両の一方。終了日時は開始以降。有効割当はタグ・社員・車両ごとに一意 |
| 専用区画 | 専用区画だけに専用車両を指定。指定先は存在する車両 |
| 履歴の登録情報 | 7項目をすべて保存するか、すべて未保存。保存後は上書き・消去不可 |

瞬時の操作をミリ秒精度で記録できるよう、実績の開始・終了が同時刻であることは許可します。予定は正の時間を必須とします。全ての予定の時間帯重複やVehicle.statusとTripのテーブル間状態一致は、既存のアドバイザリーロック・トランザクション・版番号検査を維持します。

NFC所有者のFKはRESTRICTです。通常運用の削除は無効化を使用します。専用区画のFKはJSON復元時の循環参照（区画→専用車両、車両→駐車区画）を扱うため、トランザクションのコミット時に検査する遅延FKです。

## 移行と初期化

開発も本番も`prisma migrate deploy`を使います。Prismaモデルに表しきれないCHECK・部分一意索引・トリガー・遅延FKも、番号付きSQLが正本です。`db push`で同期しないでください。既存の適用済み移行ファイルを書き換えず、追加SQLで変更します。

旧方式のdb pushで作ったDBに移行履歴がない場合は、実際のテーブル・カラムと主要な索引を確認して、既に導入済みの変更だけを履歴へ登録します。途中のカラム構成や必要な索引の欠落を見つけた場合は停止します。新しい制約に反する既存データがあれば移行を失敗させ、自動でデータを消去・補正しません。

旧形式のデータ変換用スクリプトは互換用に残していますが、現在必要な制約・索引はSQL移行だけで構築できます。新規本番構築ではサンプル社員・車両・利用記録を入れず、駐車区画だけ初期化します。

索引はTrip(vehicleId, actualStart, id)、Trip(employeeId, status)、AuditLog(targetType, targetId, createdAt)を追加しました。二重利用等を守る部分一意索引もSQLに含めています。

## バックアップ

JSON書き出しに新しい履歴項目を含めます。旧JSONに項目がなければNULLで読み込みます。入出力のformatVersion=1は維持し、新しい読み込み側で既存のファイルを扱います。旧バージョンのアプリへ新形式の項目を含むJSONを戻す用途はサポートしません。

復元前に、参照先・一意性に加えて状態と実績日時、有効な番号・NFC割当、二重利用、整備状態、履歴項目の完全性などを検査します。復元は一つのトランザクションで実行します。既存のRESTORE確認操作は維持します。

## 検証

- 12本のSQL移行による新規構築。
- 旧db push方式の開発DBを読み取って使い捨てDBへ複製し、既存データを残す追加移行。
- 通常の本番初回DB準備コマンドの使い捨て環境での実行。
- `npm run test:integration:database-hardening`：不正値・二重利用・参照切れのDB拒否、通常利用開始と予約からの開始、改名後の当時の情報保持と検索、履歴上書き拒否、開始時刻訂正、返却と返却取消、新旧JSON復元、専用区画の循環参照の復元。
- 新制約下での既存の整備・駐車位置・開始時刻・API重複抑止の統合テスト。
- 履歴期間計算、予約表示、開始時刻の入力制限、共用端末の回帰テストと型チェック。
- 分離した一時コンテナーでNext.jsの本番向けビルド成功。

統合テストは専用の使い捨てDB名・接続先を検査してから実行します。開発DB・本番DBでそのまま実行しないでください。
