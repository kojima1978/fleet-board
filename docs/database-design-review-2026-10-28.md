# FleetFlow DB設計レビュー（2026-10-28）

> 実施状況：レビュー後、優先改善1〜4（当時の表示情報、DB制約、移行の一元化、履歴索引）を実装し、開発環境へ反映しました。本文の指摘・実測値は見直し前の記録です。実装と検証結果は[DB整合性と利用開始時点の履歴](database-hardening.md)を参照してください。訂正ログの構造化、不要項目の削除、保持年数の変更は今回の実施範囲に含めていません。

## 結論

PostgreSQLと現在のテーブル分割は、このアプリの機能に概ね適しています。全面的に作り直す必要はありません。ただし、運用開始前に「当時の情報を残す履歴」「DB自身の整合性制約」「移行手順の一元化」を補強することを推奨します。履歴検索の索引も追加候補です。

このレビューではアプリの実装、Prismaスキーマ、SQLマイグレーション、初期化・バックアップ処理を確認しました。開発DBは読み取り専用トランザクションで検査しました。矛盾データの投入検証は既存環境から独立した使い捨てDBだけで行い、各操作をロールバックしました。本番DBの実物は検査していません。既存DBのデータ・構造・アプリの動作は変更していません。

## そのまま維持してよい構成

| 構成 | 評価 |
| --- | --- |
| Employee / Vehicle と固定ID | 利用記録が社員・車両の実体を参照できる。番号をIDとして使わない方式は適切 |
| EmployeeNumber / VehicleNumber | 番号の再利用と、旧社員・旧車両の記録保持を両立する意図がある。単なる重複と判断して削除しない |
| Department | 部署の共通管理として適切 |
| NfcTag / NfcAssignment | カード・タグと、社員／車両への割当期間を分ける方式は適切。QRの不変トークンも番号と独立している |
| ParkingSpot / Vehicle.parkingSpotId | 車両の現位置と区画の形状・用途を分離している。区画への同時駐車は一意索引で防いでいる |
| Trip | 予定と実績を同じ記録の別カラムとして持つ構成は現状の予約→利用→返却に適する。直ちに予約専用／実績専用テーブルへ分割する必要はない |
| VehicleMaintenance | 整備の予定・実績を別管理できる |
| AuditLog | 操作履歴と車両利用履歴を別に保持している点は適切。操作IDの一意制約もある |

## 運用開始前の優先改善

### 1. 利用当時の表示情報を保存する（優先度：高）

Tripは社員ID・車両IDと利用日時を保存していますが、社員名・社員番号・部署・車両名・車両番号・ナンバーの当時の値は保存していません。履歴APIは現在のEmployee・Vehicle・番号マスターを参照します。氏名変更、部署変更、車両番号変更などがあると、過去の履歴の表示も現在の値になります。

固定IDにより「別人・別車両になる」という問題とは区別が必要です。現在の実装は番号が同じでも実体IDで区別できます。ただし「当時どの名前・番号・所属だったか」は復元できません。

推奨方針：Tripに利用開始時の表示情報を保存します。例はemployeeNameAtStart、employeeCodeAtStart、departmentNameAtStart、vehicleNameAtStart、vehicleCodeAtStart、plateNumberAtStartです。参照IDも残します。予約時点と利用開始時点の情報を区別し、利用実績には利用開始時点の値を使います。旧記録は当時の値が不明なため、現在値からの補完を「当時の情報」と誤認させない扱いが必要です。

根拠：prisma/schema.prisma のTrip、app/api/trips/history/route.ts、社員・車両編集処理。

### 2. アプリの検査に加え、DBにも制約を置く（優先度：高）

アプリではトランザクション、アドバイザリーロック、版番号、入力検証で通常操作を保護しています。一方、DB自身には次の保護が不足しています。取込・将来の改修・直接のDB操作でも守れる形にします。

| 対象 | 追加候補 |
| --- | --- |
| Trip / VehicleMaintenance | 予定終了が開始より後であること、実績終了と開始の前後関係、状態と実績日時の整合性 |
| Trip | IN_USEについて車両ごと・社員ごとに1件だけを許す部分一意索引 |
| VehicleMaintenance | ACTIVEについて車両ごとに1件だけを許す部分一意索引 |
| Vehicle / Trip | 残量がNULLまたは0〜4であること。返却残量・取消復元用の残量も対象 |
| NfcAssignment | 社員または車両の一方だけを参照するCHECK、割当開始・終了日時の前後関係 |
| ParkingSpot | dedicatedVehicleIdの実際の外部キー化。区画用途と専用車両指定の組合せも整合性を検討 |

CHECKは同じ行の整合性、部分一意索引は「利用中の車両ごとに1件」などの複数行の条件、外部キーは参照先の存在確認に使い分けます。Vehicle.statusとTripなど、テーブルをまたぐ状態一致は単純なCHECKでは扱えません。同一トランザクションでの更新と整合性検査を維持します。予約の時間帯重複についても、現行ロックを維持した上で、必要性を確認して排他制約などを検討します。

NfcAssignmentの所有者CHECKは移行スクリプトのCREATE TABLE文にはありますが、既存テーブルには追加されず、確認した開発DBにもありませんでした。また既存の所有者FKは削除時SET NULLなので、所有者CHECKを追加するなら物理削除／無効化の方針とFKの削除動作をそろえる必要があります。

JSON復元では参照先や予定時刻の順序を検査していますが、全状態・実績時刻・二重利用などの検査は十分ではありません。DB制約と復元バリデーションを同時に強化し、「復元できるが矛盾する記録」を防ぐことを勧めます。

根拠：実DBの制約・索引、prisma/migrations、scripts/migrations/migrate-unified-nfc-assignments.mjs、lib/json-backup.ts。

### 3. 制約の作成をバージョン付き移行へ一元化する（優先度：高）

現状はPrismaのマイグレーション、開発用db push、起動時の独自移行スクリプトが併用されています。社員・車両の有効番号一意性とNFCの有効割当一意性を守る5本の部分一意索引は、独自スクリプトで作成されます。マイグレーション単独では作られません。

通常の起動手順には独自スクリプトが含まれるため、直ちに通常起動で保護が欠けているという指摘ではありません。構築方法により制約が変わりやすく、変更時の確認が難しいという保守上の問題です。

推奨方針：運用で必要な制約・索引をSQLマイグレーションへ含め、新規構築と既存DB更新の両方を試験します。独自スクリプトは旧形式のデータ変換に役割を絞り、最終スキーマの正本を統一します。既に適用した移行ファイルを書き換えるより、追加移行でそろえる方が既存の検証環境を扱いやすい構成です。

開発DBに_prisma_migrationsがないことは、現状のdb push方式では想定内です。それ自体をデータ破損とは判断していません。

### 4. 利用履歴・操作履歴の検索に合う索引を補う（優先度：中）

現在のTripの索引は(plannedStart, plannedEnd)、(vehicleId, status)です。今回追加した実績検索はvehicleId、actualStart、actualEndとactualStart順を使います。社員ごとの競合検査はemployeeIdも使います。

候補：Trip(vehicleId, actualStart, id)、Trip(employeeId, status)、AuditLog(targetType, targetId, createdAt)。必要なら状態を絞る部分索引を検討します。開始時刻訂正は同じ車両・社員の過去記録を広く取得してアプリで重複検査しているため、検索条件側の絞り込みも検討します。

開発DBのTripは23件（うちデモ18件）です。この規模で速いことは、大量履歴での性能を保証しません。索引追加の最終形は想定件数のデータとEXPLAINで確認します。現在遅延が発生していると断定するものではありません。

### 5. 訂正履歴を文章だけでなく構造化する（優先度：中）

AuditLogはactorNameを保存しており、操作者名の保存という点は良い構成です。一方、訂正前後・理由などは主にdescriptionの文章に保存しています。利用開始のログはVehicle、返却のログはTripを対象にしており、利用1回に紐づけて変更履歴を追う処理には工夫が必要です。

AuditLogに対象Tripへの一貫した関連と、変更前・変更後・理由などの構造化情報を追加する方針を推奨します。既存の表示用文章も残せます。全面的なイベントソーシングへの作り直しは不要です。

## 削除・整理を検討する項目

| 項目 | 判断 |
| --- | --- |
| Trip.purpose | 現行の利用開始・予約登録は空文字を保存しており、入力UIはない。既存のサンプルには値があるため、削除するならseed・JSON形式・旧データ取込まで一緒に整理する。将来利用目的を入力しない方針なら削除候補 |
| VehicleStatus.RESERVED | 現行の予約はTripで管理し、車両statusをRESERVEDへ変更していない。用途を確定して整理する候補。単純削除ではなく旧データ／JSONとの互換性を確認 |
| Trip.previousFuelLevel | 返却取消時に元の残量へ戻すために使用中。重複に見えても削除しない |
| plannedStart / plannedEnd と actualStart / actualEnd | 予定と実績で意味が違うため残す |
| Vehicle.fuelLevel と Trip.returnFuelLevel | 現在の残量と、その返却時点の記録で意味が違うため残す |
| version / operationId / qrToken | 同時更新、重複送信、番号の再利用から独立したQRを支える。残す |
| 通常の車両情報ポップアップから外した表示 | 表示を省略しただけなら、DB項目の削除理由にはならない |

## 保持期間とバックアップ

利用履歴・操作履歴を経過日数だけで自動削除する通常処理は見つかりませんでした。「過去1か月」は検索条件で、1か月より前の記録を削除する設定ではありません。

SQLバックアップファイルは30日より古いものを削除しますが、これはDB内の利用履歴の保持期間とは別です。保持年数・古い履歴の書き出し／削除方針を決め、JSON取込上限（Trip 200,000件、AuditLog 300,000件）や全件メモリ読込も将来件数に合わせて確認します。

履歴のために保持するマスターは通常無効化で扱い、過去記録を参照している社員・車両を物理削除しない方針を維持するのが適切です。

## 今回の実測・再現結果

開発DBを読み取り専用で検査した結果、次はすべて0件でした：予定日時逆転、実績日時逆転、利用状態と実績日時の矛盾、同一車両／社員の二重利用、車両状態と利用記録の不一致、利用可能車両の駐車位置欠落、NFC所有者矛盾、専用区画の参照切れ、不正な残量。検査時点の集計であり、あらゆる不整合がないことの証明ではありません。

別の使い捨てDBへ現在の11本のマイグレーションを適用できました。そのDBでは、次の直接保存を拒否しませんでした：予定時刻の逆転、実績時刻のない完了記録、同一車両・社員の複数IN_USE、残量999、社員と車両の両方を所有者にしたNFC割当、存在しない車両IDを参照する専用区画。

通常起動で使う社員番号・車両番号・NFC割当の移行スクリプトを追加適用した後も、上記6種類はDBレベルでは保存可能でした。一方、既存の5本の部分一意索引が追加されることは確認しました。これはDB単体の防御の検査であり、通常の画面操作で同じ不正データを登録できると実証したものではありません。すべての保存検証はロールバックし、一時DBは終了しました。

## 推奨する実施順序

1. 当時の表示情報を保持する仕様、履歴の保持期間、物理削除しない運用を確定する。
2. 必要な履歴情報・DB制約・索引を追加移行で導入し、保存処理とJSON入出力を合わせる。
3. サンプルデータを除いた新規構築と、現在の開発DBからの更新・バックアップ復元の両方を検証する。
4. 実機確認とレビュー後に本番へ反映する。
